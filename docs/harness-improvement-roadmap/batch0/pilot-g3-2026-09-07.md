## 4. 候选方案的新瓶颈（P 系列，全部可修复）

| # | 发现 | 影响 | 修复方向 |
|---|---|---|---|
| P1 | fast 档验证自动解析过重：docs-only 任务跑 npm 全链（260-286 s），g2 手工定向 doc contract 测试仅 1.19 s | T1 e2e 未达门槛的直接原因 | docs-only → doc contract test 的档位感知验证选择 |
| P5 | standard 档三项验证（compile/unitTest/unitTestFull）全部解析为同一条 npm 链，等效跑 3 遍 | T3 验证 679 s vs 单次 240 s | resolvedAs 相同的验证项去重 |
| P6 | 验证粒度错配：任务改 Python，验证只有 npm 链（node 探测 profile） | 同上 | 按变更语言/路径选验证（Python → python -m unittest） |
| P9 | finish 失败重入时，验证副作用文件（npm pretest → sync:harness 改 bundle hash）被误判 foreign | T3-r2 多 1 次重试 | 重入时重建 ownership 契约或副作用白名单 |
| P10 | flaky 测试放大墙钟：全量链单挂即整个 finish 重来（13.9 min 白跑） | T3-r2 多 13.9 min | P5/P6 修复（定向验证）天然缓解 |

**架构性结论**：候选方案把「流程维护」从 ~2.2 min 压到秒级、把「契约学习成本」清零——
原提案定位的两大成本项都被消除。剩余瓶颈全部集中在**验证选择策略**（P1/P5/P6），
这是独立的、有明确修复方向的问题，不是轻任务闭环架构的障碍。
